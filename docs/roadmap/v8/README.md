# ContentCloud V8：让复杂内容任务可以持续推进

状态：V8 目标方案；Runtime Infra V2 I1～I5 的核心切片、第二业务流容量边界测试、运营 Explorer 首版，以及终态业务结果的持久化消费链已进入代码，尚未达到生产上线条件。2026-08-09 起按 [Runtime Infra V2 升级说明](./09-runtime-infra-v2.md) 收敛底层实现顺序。

更新时间：2026-08-13

> 这份 README 先用一项实际任务说明 V8。只想了解产品方向，读到“为什么叫 Agentic Job Runtime”即可；工程设计和官方证据放在后续文档中。

## 专项定位

V8 是 [ContentCloud 平台基线](../../foundation/README.md) 下的 Runtime 专项路线图，负责执行实例、执行图、调度、状态、恢复、外部操作和运行诊断，不定义客户创作台、平台运营产品层或内容业务事实。客户产品需求位于 [`docs/product`](../../product/README.md)。

客户创作台的线性纵向切片复用 WorkTask、StageRun、SOP 和 Gate 业务能力，执行统一进入 Runtime，不等待动态执行图、共享状态和完整恢复能力全部完成，也不建立平行任务状态。

当前实现边界：客户 Studio 创建任务时会固定已发布 SOP，并以绑定摘要、输入摘要、运行策略、契约版本和根执行引用幂等启动 JobRun；运营侧统一在 `/admin/jobs` 查看 JobRun、准入身份、节点、脱敏 Agent/ContextView 摘要、事件、外部副作用和检查点。Runtime 已具备独立 `runtime_attempts` 权威模型、原子准备与终态收敛、`RuntimeCommandStore`、不可变 `runtime_outbox` 与独立 subscriber receipts、资源预留、围栏、typed state/ToolCall、Attempt-scoped MCP Gateway、Runtime Schema Registry、Provider inbox/账单对账、Yield/Resume、Codex CLI JSONL/thread resume Harness、Runtime Explorer 投影重建（含 dry-run）、关系化 GraphPatch 和 Fanout/Join。知识提取的结构化结果在终态前完成严格校验和 Blob 摘要固定，终态后由持久化业务订阅幂等写入知识对象；进程崩溃和 Explorer ack 不会丢失业务结果。V7 `task_runs/run_attempts/run_progress_events/creative_execution_bundles`、旧 daemon 领取/上报链、对应 Store/API、旧公开 DTO 名称以及零消费者 session 镜像已删除；公开读取统一为从 JobRun/NodeRun/JobEvent 生成的 `RuntimeRun` / `RuntimeRunEvent`。第二业务流已用文章复盘的 50 节点容量边界测试证明不依赖业务专用调度表；独立 CLI MCP stdio -> HTTP Gateway 本地真实传输 smoke 已通过。在线 Codex/Claude 宿主注入与模型调用、真实 Provider、真实数据库提交后故障环境、生产公平性压测、生产告警和 Canary 仍属于后续验收，不能据此宣称 V8 已完成。

## 先用一句话说明

用户提交内容需求和已批准资料后，ContentCloud 安排智能体、普通程序、外部服务商和人工完成各自适合的步骤；任务中断后可以接着做，执行过程、审核决定、费用和交付结果都有记录。

这套计划中的后台能力，工程上称为 **ContentCloud Agentic Job Runtime（智能体任务运行时）**。其中，Agentic 表示部分步骤可以由智能体完成，Job 表示一项任务的一次执行，Runtime 表示负责调度并保存执行状态的后台系统。这是产品和研发使用的架构名称，不是一个新的用户入口。

## 用一项营销任务理解

假设内容负责人要为不同受众制作 20 条短视频。任务不会一次完成，通常要经过下面这些环节：

```text
提交需求和已批准资料
        ↓
同时准备多个受众方向
        ↓
负责人审核并选择方向
        ↓
同时制作脚本、分镜和视频
        ↓
质检、审核、后期处理和交付
```

真正难处理的不是流程本身，而是执行中不断出现的变化：

- 一个方向被退回，其他方向仍应继续；
- 多项任务同时使用同一个视频服务商，需要排队并控制费用；
- 请求超时，只说明 ContentCloud 没有收到结果，不代表服务商没有执行；
- 进程或模型会话中断，已经确认完成的工作不能丢失；
- 审核结果可能要求增加、取消或调整后续步骤。

只靠一次智能体会话和一份不断改写的进度文档，很难可靠处理这些变化。V8 要增加的，是一套能跨越多天、多步骤、多人和多个服务商持续推进任务的后台机制。

## 用户会得到什么

V8 上线后，客户仍在简单的 ContentCloud 创作台中提交任务、审核内容和接收交付，不需要学习任务图或智能体框架。平台运营和支持人员通过独立 Runtime Explorer 诊断执行问题。

| 用户关心的问题 | V8 计划怎样处理 |
| --- | --- |
| 现在做到哪了 | 分别显示每个内容方向是在处理、排队、等待审核、失败还是已经完成 |
| 为什么还没完成 | 说明是在等资料、等人、等服务商，还是执行出了问题 |
| 一个方向返工会不会拖累全部内容 | 只重新处理受影响的方向，保留其他已经确认的结果 |
| 中断后要不要从头开始 | 从最近一个确认完成的位置继续 |
| 会不会因为重试而重复收费 | 每次对外请求先留记录；结果不明确时先核对，再决定是否重试 |
| 最终内容是否可信 | 可以追查使用的资料、审核决定、生成版本、费用和最终文件 |

V8 不会取消人工审核。资料是否可信、素材是否可以使用、费用是否可以接受，以及内容方向和最终交付，仍需由人工决定。系统负责排队、记录、提醒，并在规则允许时只重新处理受影响的部分。

## 先区分：工作区资料、项目参考、创作结果与交付

V8 调度的每个步骤都会读取输入并产生输出，但 Runtime 不因此拥有客户资产或交付状态。客户产品面固定区分四类对象：

| 客户概念 | 包含内容 | Runtime 的责任 |
| --- | --- | --- |
| 我的资产 | 客户明确上传或导入的文档、图片、视频、音频、表格和其他文件 | 只读取固定资料版本与摘要，不管理文件夹、上传、导入或处理状态 |
| 任务输入 / 项目参考 | 搜索结果、灵感、知识、来源证据和权利摘要 | 在输入快照和 `ContextView` 中保存固定版本引用，不自动写入客户资产 |
| 创作结果 | 流水线生成的人物原型、剧本、分镜、图片和视频结果 | 保存输出引用和执行血缘；由业务事实和结果投影决定类型、状态与是否可复用 |
| 交付作品 | 已整理、核对并可下载的 `DeliveryPackage` 和交付文件 | 记录相关步骤与外部操作，不把交付包复制成第二份资产 |

```text
我的资产 -----------+
                     +-> WorkTask -> JobRun -> NodeRun
任务输入 / 项目参考 --+                         |
                                                v
                              人物 / 剧本 / 分镜 / 图片 / 视频
                                                |
                                        +-------+-------+
                                        |               |
                                        v               v
                                  客户“创作结果”      独立交付视图
```

只有 `confirmed` 和 `delivered` 的生成结果可作为新任务的正式复用输入。普通工作区资料使用独立处理状态，不进入结果确认状态机。完整决策见 [ADR-0013](../../foundation/decisions/ADR-0013-customer-result-asset-boundary.md) 与 [ADR-0014](../../foundation/decisions/ADR-0014-customer-asset-surface.md)。

## 先区分：当前已经有什么，V8 还要增加什么

下面的“当前”指 2026-08-09 的仓库实现；V8 一栏是仍需生产验收或尚未开放的目标能力。

| 能力 | 当前仓库 | V8 计划 |
| --- | --- | --- |
| 用户任务、流程阶段和人工审核 | 已能创建任务、推进阶段和记录审核 | 保留现有入口，增加一次完整执行的进度和历史 |
| 单个后台步骤的运行 | 已能启动、监控和取消本地执行 | 将每个步骤纳入整项任务的进度和历史 |
| 我的资产工作区 | 已实现文件夹、上传、预览、固定引用、加入任务和最近使用；连接器导入与 AI 理解待完成 | V8 只消费固定资料引用；文件与组织关系仍由客户工作区拥有 |
| 任务输入与项目参考 | 已能管理来源、知识、素材和任务内灵感 | 只固定输入版本和最小上下文引用，不自动将它们投影为客户资产 |
| 创作结果 | 已能投影人物原型、剧本、分镜、图片和视频结果 | 关联执行输出与血缘，不接管结果类型、审批和复用状态 |
| 交付结果 | 已能管理媒体文件和交付包 | 关联每次执行和外部操作，交付决定继续由业务域拥有 |
| 同一任务重新执行或换一条路线 | 还没有独立的一次执行记录 | 新执行保留旧历史，不在原记录上覆盖 |
| 同时推进并根据结果调整步骤 | 当前主要按预先安排的阶段顺序执行 | 允许多个方向同时推进，并根据审核或执行结果增加、取消或汇总后续工作 |
| 多个步骤共享进度和业务数据 | 还没有带固定格式、权限和版本保护的专用记录 | 增加同一次执行内的共享状态，防止并发修改互相覆盖 |
| 中断后继续 | 还没有面向整项任务的明确续跑位置 | 记录已经确认完成的位置，只继续未完成的部分 |
| 外部视频生成 | 已有完整领域对象和测试链路；当前内置适配器只有本地模拟服务商 | 先完成请求登记、结果核对和费用治理，再接入真实测试服务商 |

当前基线以代码和变更记录为准，详细依据见 [08-migration-testing-and-acceptance.md](./08-migration-testing-and-acceptance.md) 的“当前基线对账”。历史路线图不能代替当前实现。

## V8 准备怎样解决

### 1. 后续步骤可以根据结果调整

固定流程只能按预先写好的顺序执行。实际生产中，不同方向需要同时推进，审核结果也会决定后面增加、取消或汇总哪些工作。

V8 计划允许系统在执行中调整后续步骤。研发文档把这些步骤及其先后关系称为**动态执行图（动态 DAG）**。这种调整必须遵守步骤数量、层级、并发和预算上限，不能无限拆分或循环。

### 2. 多个步骤共用一套可靠记录

不同步骤都需要知道哪些方向已经批准、文件在哪里、预算还剩多少。V8 计划把这些信息保存成有固定字段、访问权限和修改历史的记录，研发文档称为 **Job 内共享状态**。

它不是一篇由智能体反复改写的进度文档。两个步骤同时修改同一条记录时，系统会发现版本冲突，避免后提交的内容悄悄覆盖先前修改。

### 3. 中断后从确认完成的位置继续

系统会记录已经完成的步骤、采用的数据版本和产物位置。进程中断后，它会先核对这些记录，再继续未完成的工作。研发文档把这个续跑位置称为**检查点（Checkpoint）**。

检查点不是电脑内存的完整备份，也不能撤销已经收费、发布或发送到外部系统的操作。

### 4. 外部请求先留记录，再核对结果

视频生成、内容发布和发送交付链接都会在 ContentCloud 之外产生实际影响。网络超时后直接重试，可能重复执行或重复收费。

V8 计划先登记请求，再查询服务商结果。确认没有执行后才自动重试；仍然无法确认时，暂停这一步并请人处理。

### 5. 并发和费用都有上限

系统会统一管理模型用量、服务商并发、任务优先级和预算。可以同时处理的工作尽量并行，但任何任务都不能无限创建步骤或持续消耗资源。

## Codex 和 Claude Code 负责什么

Codex 和 Claude Code 适合完成需要阅读资料、调用工具和根据结果作判断的具体步骤。固定解析、格式校验、文件转换和确定性渲染等工作，继续交给普通程序。

ContentCloud 负责整项任务的业务状态、排队、审核、费用、中断恢复和外部操作记录。不能把一次模型会话、子智能体列表或模型自己的待办事项当成业务数据库。

已经核对的官方资料表明，Codex 和 Claude Code 支持会话、工具调用和一定形式的子智能体协作；没有证据表明它们直接提供了 ContentCloud 所需的完整业务运行时。具体能力、限制和官方链接见 [02-host-capability-evidence.md](./02-host-capability-evidence.md)。

## 为什么叫 Agentic Job Runtime

V8 不是传统 IT 语境里的操作系统。它不管理整台机器的进程、内存、磁盘和设备，只负责 ContentCloud 中一项有明确边界的内容任务。

因此，“Agent OS”可以作为宽泛比喻，但 **Agentic Job Runtime** 更准确：

```text
用户：提交需求、审核关键决定、接收交付
ContentCloud：安排整项任务、保存业务记录、控制费用和风险
Codex / Claude Code：完成适合由智能体处理的具体步骤
普通程序 / 外部服务商：完成校验、转换、渲染和视频生成等工作
```

## 明确不做

- 不把 ContentCloud 做成管理整台电脑或所有应用的操作系统。
- 不让系统无限创建智能体、无限循环或在运行中自行修改规则。
- 不执行客户上传的任意代码，也不在服务端请求中直接运行不受约束的通用智能体。
- 不让智能体自动批准事实、素材权利、费用、脚本、分镜或最终成片。
- 不把 Codex 或 Claude Code 的会话和子智能体清单当作 ContentCloud 的业务数据库。
- 不承诺把外部世界恢复到过去，也不承诺外部调用一定只发生一次。
- 在动态执行、共享状态、中断续跑和真实服务商都通过验收前，不对外宣称已经具备完整的智能体任务运行能力。

## 决策记录

| 日期 | 决策 | 原因 |
| --- | --- | --- |
| 2026-08-04 | 定位为 ContentCloud Agentic Job Runtime | 比“Agent OS”准确：只负责一项有边界的业务任务，不管理整台计算机 |
| 2026-08-04 | 用户任务与一次执行分开保存 | 重新执行或换路线时保留旧历史，不覆盖用户原始请求 |
| 2026-08-04 | Codex 和 Claude Code 作为步骤执行者 | 智能体会话和任务清单不能替代 ContentCloud 的业务记录、费用和外部操作治理 |
| 2026-08-04 | 首版只做有上限的动态执行图和有固定格式的共享状态 | 先把规模、权限和故障行为做成可验证的工程约束 |
| 2026-08-06 | V8 使用独立 `RuntimeAttempt`；旧 `RunAttempt` 已随 `00034` 删除 | 两者关联的执行实例和状态机不同，复用或兼容适配会形成错误外键和双重事实源 |
| 2026-08-06 | Harness 由进程级 Registry 显式注入 | Fake/CLI 会话保存在适配器实例中，每次选择时重建会导致会话引用不可恢复 |
| 2026-08-06 | 外部 Harness 调用采用 Prepare/Start/Activate/Finalize 协议 | 数据库事务不能包住外部进程；分阶段原子提交和租约恢复可以覆盖每个崩溃窗口 |
| 2026-08-07 | Runtime 只引用工作区资料、任务输入、生成结果与交付事实 | 防止执行状态、文件处理、客户结果状态和交付状态形成平行事实源 |
| 2026-08-08 | 先升级 Durable Runtime 内核，再开放动态图和真实宿主恢复 | 当前代码已具备一次调度闭环，但事务原子性、资源账本、跨进程恢复和外部 unknown 对账仍不足以支撑生产扩展 |
| 2026-08-15 | Seedance 2.5 先作为受 ContentCloud 控制的单镜头 Provider 接入 | 复用现有 Media Job、Effect、费用和 Artifact 血缘，不把外部 MCP 或完整应用变成第二套控制面 |
