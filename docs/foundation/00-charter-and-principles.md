# 平台宪章与设计原则

状态：`目标规范`。

更新时间：2026-08-05。

## 1. 真正要解决的问题

ContentCloud 当前已经拥有来源、知识、SOP、审核、媒体和交付等丰富能力，但客户仍可能面对项目、知识治理、Agent 安装、SOP 和执行环境等内部概念，不知道从哪里开始以及下一步做什么。即使客户完成了一次任务，也缺少一个能理解、能搜索、能安全复用历史成果的统一资产入口。平台运营人员则缺少一套可以稳定发布、验证、启用和回退客户创作场景，并持续治理创作资产的产品机制。

本轮重构解决两类结果：

- **客户结果：** 客户不理解平台内部模型，也能完成一条真实创作流水线。
- **创作资产结果：** 每次流水线生成、确认和交付的人物原型、剧本、分镜、图片和视频，都能在治理边界内沉淀为下一次可复用输入；来源和灵感仍属于任务输入或项目参考。
- **平台结果：** 运营人员不修改客户页面和 Runtime 核心，也能持续发布受治理的创作产品。

## 2. 产品定义

ContentCloud 是一个由简单客户体验、平台运营控制面和可治理任务运行时组成的内容创作平台。

它不是：

- Codex 或 Claude Code 的 Web 外壳。
- 把所有创作功能堆在一起的通用后台。
- 允许客户自由编程的低代码工作流市场。
- 自动替代事实、权利、费用和最终内容决定的无人系统。

## 3. 目标用户与价值

| 角色 | 核心工作 | 产品承诺 |
| --- | --- | --- |
| 客户创作者 | 提交资料、选择方向、复用资产、修改内容、取得交付 | 始终知道当前结果和唯一下一动作 |
| 客户审批人 | 确认方向、版本、费用和风险 | 每次决定绑定固定版本并可追溯 |
| 租户管理员 | 管理成员、资产访问和租户允许项 | 不接触平台级密钥和 Runtime 内部配置 |
| 平台内容运营 | 维护场景、体验模板、SOP、门禁、资产治理和租户启用 | 不改代码即可发布已批准组合 |
| 平台运行运营 | 管理执行者、服务商、预算、故障和对账 | 能从客户步骤定位到底层执行事实 |
| 执行能力开发者 | 开发 Worker、连接器、业务包和 Agent 适配器 | 使用稳定契约扩展，不依赖内部数据库 |

## 4. 十二个月理想态

```text
当前状态
本地优先工作台 + 线性 SOP + 丰富但横向聚合的领域能力
        |
        v
本轮基线
产品面分离 + 事实所有权 + Runtime 边界 + 模块/契约/迁移规范
        |
        v
十二个月理想态
客户场景产品化 + 可治理流水线平台 + 可恢复执行 + 可持续运营经济
```

理想态不是“Runtime 功能最多”，而是同时满足：

- 客户在几分钟内开始场景，并在可预测时间内取得首个可确认结果。
- 运营人员可以草拟、验证、Canary、发布、租户启用、回退和停用场景版本。
- 第二条结构不同的流水线只增加业务包和契约，不增加专用调度表。
- 本地 Agent、托管执行、确定性 Worker 和服务商可以按数据与预算策略替换。
- 任务中断、部分失败和外部结果不明时可以恢复且不会重复批准或盲目重试。

## 5. 核心原则

### 5.1 体验简单，内核严格

客户页面只展示业务目标、必要输入、业务进度、结果、阻断和动作。版本固定、权限、幂等、预算、租约、重试和对账由内核承担。

### 5.2 执行事实与业务事实分离

Runtime 拥有 Job、Node、Attempt、Lease、Effect 和执行事件。Source、Knowledge、Submission、Approval、Artifact、Delivery 等对象由对应业务域拥有。Runtime 使用不可变引用，不复制或修改业务事实正文。

### 5.3 能力与执行者分离

流水线只声明 `source.search`、`content.script.propose`、`media.generate` 等能力。执行绑定根据租户、数据位置、隔离、区域、预算和健康状态选择具体实现，并固定到执行计划。

### 5.4 候选与正式事实分离

Agent、模型、搜索、网页和服务商输出默认是候选。客户选择不等于事实批准，模型置信度不等于证据和权利门禁。

### 5.5 版本优先于“最新”

模板、SOP、Schema、能力、绑定、输入和批准结果都使用固定版本或摘要。新发布不改写进行中的任务。

### 5.6 渐进替换优先于大重写

先旁路编译、双读比较和兼容适配，再切换权威写入；每个旧路径只有达到明确对账和回退门槛后才退场。

### 5.7 受限组合优先于无限配置

运营人员组合已批准的体验原语、业务包、能力和门禁。新代码、连接器或执行模式必须经过工程发布，不允许在控制台粘贴脚本。

### 5.8 模块化单体优先

先通过 Go package、窄接口、事务边界、数据库权限、BFF 和依赖检查获得隔离。只有真实指标证明需要时才引入跨服务网络和分布式事务。

### 5.9 每次创作都沉淀为可复用结果资产

流水线生成的人物原型、剧本、分镜、图片和视频结果，通过统一只读目录被客户发现。来源、灵感、知识、权利记录和参考素材继续停留在当前任务或项目参考范围，不与结果资产混成同一客户列表。目录只引用各业务域事实，不复制正文；新任务固定底层对象版本和摘要。平台复利来自更少的重复采集、生成和审核，而不是目录项数量本身。

## 6. 产品成功指标

### 6.1 客户

- 创建任务到首个可确认结果的 P50 / P95 时间。
- 无帮助完成首个场景的比例。
- 每阶段完成、退回、阻断和人工求助比例。
- 客户找到下一动作所需的主要操作次数，目标不超过两次。
- 新任务复用已有来源、批准内容或成果的比例，以及重复上传下降比例。

### 6.2 运营

- 从业务包批准到场景发布的时间。
- 模板复用率和每租户覆盖项数量。
- 目录中待审核、失效、重复和即将过期资产的处理时间。
- Runtime 故障平均定位和恢复时间。
- 单任务成本、人工介入率和外部结果对账率。

### 6.3 平台

- 第二条流水线修改 Runtime 核心文件的数量，目标为零。
- 兼容层数量、年龄和按期退场率。
- 任务恢复成功率、重复副作用率和状态对账差异率。
- 契约兼容、跨租户隔离和发布门禁通过率。
- 资产目录投影延迟、重建成功率和失效传播时间。

## 7. 停止和回看条件

- 首个客户切片没有改善完成率或首个结果时间：停止扩展 Runtime，先修正体验和任务设计。
- 新业务流需要内容类型专用调度表：停止业务扩展，重新评审领域与 Runtime 契约。
- Runtime 状态或投影无法确定性对账：停止新准入和扩大范围，保留权威历史并前向修复 Runtime/投影。
- 运营覆盖项和人工维护随租户线性增长：收敛体验原语，不继续接受自由定制。
- 资产目录随原始搜索结果无限增长或查找时间没有改善：停止扩展分类和智能检索，先收紧收录策略。
- 外部副作用结果不明仍能自动重试：阻断发布，不以业务速度为由放宽。

## 8. 不在本轮范围

- 一次性搬迁全部目录、表和 API。
- 通用拖拽工作流编辑器。
- 企业级 DAM、全盘同步网盘、三维资产画布或任意关系图；客户资产入口所需的最小文件夹、上传/导入和基础预览属于明确产品范围。
- 客户上传执行代码或自定义爬虫。
- 无人工门禁的事实、权利、费用和最终交付批准。
- 在没有真实平台回执时宣称已经发布到抖音或公众号。
- 因产品面分离而立即拆成多个微服务或独立仓库。

## 9. 已有能力基础

当前仓库已经具备可复用的 WorkTask、StageRun、Runtime 只读 TaskRun 投影、JobRun/NodeRun/RuntimeAttempt、SOPVersion、StageDefinition、GateDefinition、Capability、Source、EvidenceSpan、Knowledge、SubmissionRevision、ApprovedSnapshot、Artifact、DeliveryPackage、项目投影、管理员 Shell 和客户工作台。V7 RunAttempt 执行模型已删除，不再属于可复用能力。

这些对象已经构成客户资产入口的事实基础。本轮目标是澄清工作区资料、创作结果与治理对象的所有权，收紧依赖并补齐产品层与 Runtime 关系，不重建这些业务对象，也不把现有 `Asset` 扩张成超级聚合。
