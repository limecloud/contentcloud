# ContentCloud 平台基线

状态：`平台基线已建立；首批 Studio、资产与 Runtime 切片已落地，后续变更继续接受产品、运营、工程、安全与设计联合评审`。

更新时间：2026-08-08。

## 1. 文档定位

本目录定义 ContentCloud 下一阶段及后续迭代共同遵守的平台基线。它不是某一个版本的功能清单，也不是已经上线能力的说明，而是产品边界、业务事实、Runtime、代码组织、契约、质量和迁移的规范来源。

基线目标只有一个：未来增加新的创作流水线时，主要扩展业务包、Schema、能力绑定和客户体验模板，不再复制任务状态、重新发明审批交付对象或把平台内部概念暴露给客户；客户带入平台的资料可以持续整理，每次生成并确认的创作结果也能沉淀为下一次可直接引用的资产。

## 2. 一句话架构

```text
客户使用简单的创作台完成目标
        |
平台运营使用独立控制台发布受治理的创作产品
        |
Agentic Job Runtime 协调执行但不侵占业务事实
        |
Worker、本地 Agent、服务商和人工完成各自适合的节点
        |
客户资料与生成结果进入同一资产入口的不同投影，按各自规则被下一次任务固定引用
```

## 4. 文档事实层级

不同文档承担不同责任，禁止相互冒充：

| 层级 | 事实来源 | 作用 |
| --- | --- | --- |
| 当前实现事实 | 代码、数据库迁移、契约、自动化测试、变更记录 | 说明系统今天真实具备什么 |
| 平台规范 | 本目录 | 说明后续设计和实现必须收敛到什么边界 |
| 专项路线图 | `docs/roadmap/v8` 等 | 说明某一能力如何分阶段实现 |
| 产品叙事规范 | `docs/product/00-product-narrative.md` | 说明同一平台事实怎样向客户、运营和工程分层表达 |
| 场景产品需求 | `docs/product/customer-creation-studio` | 说明具体客户场景如何使用平台基线 |
| 横向产品需求 | `docs/product/creative-asset-library` | 说明跨任务资产如何积累、治理和复用 |
| 对外用户文档 | `docs/content` | 只说明已验证、可执行的当前能力 |

当目标规范与当前代码不一致时，必须明确标记为迁移差距，不能把目标写成已经实现。对外文档不得仅凭本目录提前宣布能力可用。

## 5. 固定不变量

1. 客户创作台和平台运营控制台是不同产品面，不是同一后台隐藏高级菜单。
2. Runtime 是唯一执行事实源；业务域仍拥有来源、知识、审批、产物和交付事实。
3. 同一任务状态只保存一次，客户和运营读取不同投影。
4. Codex、Claude Code、Worker、服务商和人工都是执行者，不能自行批准或扩大权限。
5. 流水线声明能力，发布或准入阶段绑定具体执行者，运行中不静默换绑。
6. 任务开始时固定体验模板、SOP、执行计划、能力绑定和输入摘要。
7. 候选结果只有通过来源、权利、质量和人工门禁后才能成为正式输入。
8. 兼容层必须有所有者、指标、退场条件和最晚清理阶段。
9. 模块化单体优先，只有负载、故障隔离或组织所有权证明需要时才拆服务。
10. 发布声明必须区分目标、预览、已实现和已投产。
11. 客户“资产”是统一入口，不是统一写模型；它组合客户上传/导入的工作区资料与流水线生成结果两个专用投影。
12. 搜索候选、来源证据、知识治理、权利记录和 Runtime 事件不会自动成为客户资产；只有客户明确导入的资料或正式生成结果进入对应视图。
13. 创作结果投影只表达人物原型、剧本、分镜、图片和视频；已确认或已交付结果才能正式复用，结果状态不能强加给普通文件。
14. 所有资产引用固定底层对象版本和摘要，目录项与文件夹本身不成为 Runtime 权威输入或业务正文拥有者。
15. 客户叙事中心是 Content Work OS 创作任务，不是万能 Agent；供应商只作为可替换执行者或工具示例。

## 6. 现有对象与模块处置规则

所有现有对象、模块和接口必须进入下列一种处置状态：

| 状态 | 含义 |
| --- | --- |
| `current` | 当前受支持且允许继续演进；扩展或改名是动作，不是生命周期状态 |
| `compat` | 当前仍为兼容或迁移所需；不得承载新产品语义，必须写明所有者和退场条件 |
| `deprecated` | 已有替代路径，禁止新增依赖；只保留有限读取或旧调用窗口 |
| `dead` | 已无运行、迁移、审计或文档入口价值；完成引用核对后删除 |

不得使用“以后重构”、`Reuse`、`Extend` 或 `Rename` 代替生命周期状态。保持、扩展、改名、迁移和删除必须写在独立动作列；每个 `compat`、`deprecated` 和 `dead` 项必须进入 [07-migration-and-delivery.md](./07-migration-and-delivery.md) 的处置矩阵。

## 7. 变更治理

以下变更必须新增或更新 ADR：

- 产品面合并或拆分。
- 业务事实所有权变化。
- 核心聚合、状态机或版本语义变化。
- Runtime 与业务域边界变化。
- 新的跨模块同步依赖或独立服务。
- 新的执行模式、数据披露等级或外部副作用类型。
- 破坏兼容性的 API、Schema、事件或目录变更。
- 绕过本基线固定不变量的任何例外。

普通字段扩展、文案调整和单模块内部重构不需要 ADR，但仍需相应测试和文档更新。
