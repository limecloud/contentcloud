# ADR-0015：建立独立的平台运营后台

状态：`Proposed`。

日期：2026-08-08。

决策者：产品、平台工程、内容运营和运行运营共同评审。

关联：

- [产品平面与使用边界](../01-product-planes.md)
- [平台运营后台方案](../../product/operations-control-plane/README.md)
- [运营后台工作流、上线与清理计划](../../product/operations-control-plane/03-workflows-and-migration.md)

## 背景

ContentCloud 已经同时拥有客户创作台、任务运行底层、来源/审批/交付等业务事实，以及 Codex、Claude Code、Worker、外部服务和人工等执行方式。当前管理员页面仍然把 SOP、Gate、Capability、Environment 和运行信息拼在一起：

- 运营人员按技术名词找功能，不知道一个客户产品应该从哪里发布。
- 客户产品容易被写死到某个 Skill、客户端或服务商，换执行方式会牵动客户页面。
- 运行排查只能看到底层记录，无法从客户步骤一路追到版本、执行方式和外部请求。
- 创作结果目录已经出现，但权利失效、重复候选和投影延迟没有独立治理入口。

继续在一个 `AdminWorkOSPage` 里增加菜单，会让页面越来越大，也会把客户产品、平台配置和运行事实混成一套状态。这个问题已经不是界面整理可以解决的，需要固定产品面和事实所有权。

## 决策

建立独立的 **平台运营后台（Operations Control Plane）**，与客户创作台和 Runtime Explorer 分开组织：

```text
客户创作台
  关注：我要完成什么、需要什么资料、确认什么、得到什么结果

平台运营后台
  关注：发布什么产品、开放哪些能力、怎样选择执行方式、如何治理风险

Runtime Explorer
  关注：任务实际执行到哪、哪里失败、外部结果是否核对、如何安全恢复
```

运营后台固定六个工作面：

1. 总览与待办。
2. 创作产品发布中心。
3. 能力与执行方式目录。
4. 绑定规则和模拟器。
5. 运行诊断与外部结果对账。
6. 创作结果治理，以及租户、审计、费用和支持等平台治理。

对象关系固定为：

```text
创作产品 -> 能力 -> 技能包 -> 执行方式 -> 连接/外部服务
任务开始时按绑定规则生成不可变运行快照
```

Experience 只引用 Capability，不直接引用 Skill、Codex、Claude Code 或 Provider。运行开始后固定 `ExecutionBindingSnapshot`，后台规则变化不能静默改动进行中的任务。

运营写操作必须使用有权限、幂等、带版本检查、带原因和可审计的领域命令。Runtime 和业务事实只能由各自拥有模块修改；运营后台只通过专用命令或读模型访问。

## 备选方案

### 方案 A：继续扩展现有 Admin 页面

优点：改动少、短期看起来快。

代价：客户产品和技术配置继续混在一起；权限和状态难以分清；每增加一个能力都要修改大页面；无法形成稳定的运营工作流。

结论：不采用。

### 方案 B：为每个技术对象建立独立 CRUD 页面

优点：目录清楚，工程实现直接。

代价：运营人员仍然需要自己理解对象关系；发布一个客户产品要跨多个页面来回配置；容易产生任意修改和重复状态。

结论：不采用。技术对象可以有目录页，但必须由“创作产品发布中心”和“绑定规则”串起业务流程。

### 方案 C：建设任意低代码流程编辑器

优点：表面上灵活，能快速拼出很多流程。

代价：权限、版本、资料范围、外部副作用、成本和回退很难统一；运营人员可能直接创建不可维护的流程；客户体验会被内部配置反向污染。

结论：不采用。只提供受限的 Experience、Stage、Gate、Capability 和结果呈现原语。

## 事实所有权与边界

| 事实 | 权威所有者 | 运营后台权限 |
| --- | --- | --- |
| 客户产品版本、步骤和租户启用 | Catalog / Experience | 创建、验证、发布、回退、停用 |
| 能力、技能包、执行方式和绑定规则 | Catalog / Integration / Runtime binding | 注册、审核、模拟、发布、暂停 |
| 任务、步骤、尝试、租约、外部请求 | Runtime | 查询、暂停/取消允许范围、创建对账或新尝试 |
| 来源、权利、审批、Artifact、Delivery | 各自业务模块 | 查询影响、创建治理待办，不能直接改写 |
| 客户创作结果目录 | Experience projection | 修复投影、处理重复候选和权利影响 |
| 审计、费用和支持案例 | Platform governance | 追加记录、查询和处理，不可删除历史 |

## 兼容与迁移

1. 现有 `/admin` 路由保留，逐步把旧页面拆入新的工作面；不在没有调用量、历史可读和回退证据时删除。
2. 当前“运行基础设施”标题和 `AdminWorkOSPage` 首页在 O1 进入兼容状态；O1 完成后，首页改为“运营总览”，旧页面不得继续作为后台首页或承载新领域能力。
3. 现有 `work-os` 概览可以作为过渡数据源，但新总览必须逐步切换到运营专用读模型。
4. 当前环境、SOP、Gate、本地能力等混合配置在 O2-O4 分别迁入创作产品、能力运营、执行端和选择规则；旧配置面不得继续增加新写操作。
5. 旧的宽 Store、全局 Service 和混合 DTO 进入兼容清单；新代码不得继续扩展。
6. 运营后台的发布、绑定、诊断和资产治理按 O0-O7 阶段交付，每阶段独立开关、对账和回退。

## 安全与运行影响

- 客户、租户管理员、运营、支持和平台管理员使用不同权限范围；隐藏菜单不是权限控制。
- 技能包、执行方式、连接和服务商凭据只显示摘要和健康状态，不显示明文。
- 运行快照防止后台规则变化影响进行中的任务。
- Effect `unknown` 必须先对账，禁止重复外部请求。
- 投影重建不得触发模型、搜索、Provider 或发布等外部副作用。
- 所有发布、回退、绑定和高风险恢复操作写入审计，并提供支持编号。
- 总览和列表显示数据更新时间、延迟和来源，陈旧读模型不能伪装成实时状态。

## 验证

接受该 ADR 前，至少完成：

1. 一套 Experience 可以从草稿经过验证、Canary 发布并安全回退。
2. 一个任务开始后修改绑定规则，运行快照仍保持不变。
3. 本地 Codex/Claude Code 离线时，系统能等待或使用已批准的安全回退。
4. Effect unknown 只能进入对账流程，不能重复提交。
5. 从客户步骤可以找到对应运行、失败位置、执行方式和审计记录。
6. 创作结果权利失效可以阻止新的不安全引用，投影重建可复现且无外部副作用。
7. `1440 x 1000`、`390 x 844` 和 `320px` 页面没有横向溢出，客户页面不出现运营内部术语。

## 回退

若试点中出现权限扩大、跨租户数据、重复外部请求、严重成本异常或客户流程阻断：

1. 停止新版本、绑定规则或新运营入口的流量。
2. 恢复上一份已验证的产品/规则版本。
3. 保留已经生成的任务、运行、审计和结果历史。
4. 对受影响任务创建显式支持案例或恢复分支，不直接覆盖状态。
5. 完成原因、影响和再次开放条件后再扩大范围。

## 后果

正面：客户页面保持简单；运营后台按工作分区；执行方式可以替换；运行和资产风险有明确入口；版本和回退可追溯。

代价：需要新增 Operations BFF、运营读模型、权限矩阵和审计命令；旧 Admin 页面会有一段兼容期；产品、工程和运营必须共同维护能力目录和支持手册。

新增约束：任何新增后台功能都必须说明属于哪个工作面、谁拥有事实、如何授权、怎样回退，以及达到什么条件后删除旧入口。
