# 开发者体验与流水线开发规范

状态：`目标规范；配套脚手架和命令尚未实现`。

更新时间：2026-08-05。

## 1. 目的

平台基线只有在开发者能够沿一条可重复、可诊断、可升级的路径交付新流水线时才真正成立。本规范定义内部平台工程师和创作业务包开发者的默认工作方式，防止每条流水线重新选择目录、测试方式、错误格式和发布流程。

目标不是建立一个无限扩展的开发者平台，而是为当前明确需要的两类扩展提供一条铺好的道路：

- 在不修改 Runtime 核心的前提下增加创作业务包、Schema、SOP、Gate 和呈现配置。
- 在保持契约兼容和迁移可回退的前提下演进 Runtime、连接器、执行者和平台模块。

## 2. 主要 Persona

### 2.1 创作业务包开发者

通常由内容产品、应用工程和领域专家协作承担，负责把人物原型、剧本、分镜、营销视频或其他场景做成可发布的 `CreativePack`。

他们需要：

- 从受支持模板开始，而不是复制已有业务目录。
- 在本地使用 Fixture 验证 Schema、SOP、Gate、确定性校验和客户呈现。
- 只依赖公开契约，不理解 Runtime 数据库、租约和调度内部实现。
- 在没有真实服务商费用和生产数据的情况下完成大部分开发。
- 清楚知道一个失败来自业务包、执行绑定、Runtime、外部服务商还是客户输入。

### 2.2 平台工程师

负责 Runtime、Catalog、业务模块、BFF、持久化、集成适配器、迁移和平台级质量门禁。

他们需要：

- 快速定位事实所有者和允许的依赖方向。
- 用同一组契约测试验证 Memory、PostgreSQL、Worker、Agent 和 Provider 实现。
- 重放执行与投影而不产生真实外部副作用。
- 比较新旧路径摘要，并在 Canary 失败时回退权威路径。
- 从关联 ID、固定版本和安全诊断包还原一次失败，而不依赖聊天记录或人工猜测。

支持人员、运营人员和安全评审者是重要消费者，但不通过修改代码完成日常操作；他们使用运营控制台、Runtime Explorer、审计和运行手册。

## 3. 铺好的开发路径

新增流水线的默认旅程固定为：

```text
选择已批准场景模板
  -> 声明 manifest 与兼容 Runtime 范围
  -> 定义输入/输出 Schema
  -> 组合 SOP、能力和 Gate
  -> 增加确定性校验与 Fixture
  -> 映射客户步骤和结果呈现
  -> 声明哪些保存/批准结果进入资产目录
  -> 本地验证与预览
  -> 契约/集成/体验测试
  -> 运营草稿与 lint
  -> Preview tenant
  -> Canary
  -> 分批发布或回退
```

只有下列情况才需要平台工程师修改 Runtime：现有公开契约无法表达一个已经由至少两条真实业务流证明的稳定执行语义。单一内容类型的字段、文案、Prompt、校验和展示差异不能成为 Runtime 变更理由。

## 4. 业务包工作区规范

业务包的逻辑结构遵循 [05-contracts-and-extension.md](./05-contracts-and-extension.md)，实现时只创建实际使用的目录：

```text
creative-packs/<pack-id>/
├── manifest.*
├── contracts/              业务输入、候选结果和正式输出 Schema
├── workflows/              SOP、Gate 和能力引用
├── validators/             确定性、无网络、可重复校验
├── presentation/           客户步骤和结果呈现映射
├── fixtures/
│   ├── minimal/            最小合法输入
│   ├── happy/              标准成功路径
│   ├── invalid/            可操作的失败样例
│   ├── edge/               空值、边界、部分完成和冲突
│   └── upgrade/            旧版本兼容与迁移样例
├── tests/
└── CHANGELOG.md            契约、迁移和运营影响
```

这里的路径是目标约定，不要求在没有首个真实业务包时预先创建空目录。最终物理位置由代码组织 ADR 冻结，但各类目录内容的职责和测试要求不得改变。

## 5. 本地开发分层

### 5.1 Level 0：静态验证

不启动服务即可完成：

- manifest、Schema、引用、版本和摘要校验。
- SOP 无环、输入可达、Gate 完整和能力存在性检查。
- Fixture 与期望错误码校验。
- 禁止依赖、密钥和受限数据扫描。

这是每次保存和 CI 的快速反馈层，目标是在普通开发机上数秒内给出结果。

### 5.2 Level 1：确定性本地运行

使用 Memory Repository、固定时钟、固定 ID、Fake Executor 和本地 Blob：

- 从 Fixture 创建 WorkTask 和 JobRun。
- 执行线性计划、人工 Gate、失败、重试和恢复。
- 生成 Studio、CreativeAssetCatalog 与 Operations 投影快照。
- 记录事件、状态变化和产物摘要，但不访问网络。

默认开发命令必须停留在此层，不能因为运行测试而调用真实模型、搜索 API、媒体服务商或生产数据库。

### 5.3 Level 2：模块集成

按需启动 PostgreSQL、Worker、投影和 BFF，验证事务、RLS、租约、并发、幂等和前后端契约。Memory 与 PostgreSQL 必须运行同一套 Repository 契约测试，禁止只让其中一种实现通过。

### 5.4 Level 3：受控外部沙箱

只在显式选择、独立凭据、费用上限和测试租户下运行真实 Agent 或 Provider。测试必须记录 provider、区域、模型、版本、费用和数据披露等级，不得自动从 Level 1 或 Level 2 升级到本层。

## 6. 统一开发入口

实现阶段必须提供一个仓库级入口，具体采用 Make、Go 工具或内部 CLI 由 ADR 冻结，但开发者不应拼接多个内部脚本才能完成常见任务。入口至少提供以下稳定语义：

| 动作 | 必须完成的结果 |
| --- | --- |
| `init` | 从批准模板创建最小业务包，不复制其他场景 ID |
| `validate` | 校验 manifest、Schema、SOP、Gate、引用和禁止依赖 |
| `test` | 运行 Fixture、契约、确定性执行和投影测试 |
| `preview` | 使用本地 Fixture 展示 Studio 客户步骤和运营摘要 |
| `diff` | 比较业务包版本、Schema、执行计划和客户体验变化 |
| `doctor` | 检查工具链、服务、凭据范围和沙箱可用性 |
| `publish --dry-run` | 生成发布计划、风险、租户范围和回退条件，不改变状态 |

所有动作必须支持结构化输出，供 CI、Codex、Claude Code 和其他自动化执行者消费；面向人的输出可以更易读，但不能包含另一套语义。

## 7. Fixture 与确定性规范

Fixture 是开发、评审、调试、迁移和文档示例的共同事实，必须：

- 使用稳定 ID、固定时间、固定随机种子和规范化序列化。
- 不包含生产客户数据、Cookie、密钥、真实个人敏感信息和本地绝对路径。
- 显式声明输入 Schema 版本、业务包版本、SOP 版本和期望摘要。
- 为 `nil`、空集合、无效枚举、摘要冲突、权限不足、超时、部分完成和重复提交提供样例。
- 对 LLM 结果比较结构、引用、约束和质量评分，不比较整段文字是否完全一致。
- 对外部服务优先使用最小录制响应或手工 Fixture，并剥离敏感字段和不稳定头信息。

修复线上问题时，先建立最小脱敏回归 Fixture，再修复实现。不能把生产导出文件直接提交到仓库。

## 8. 契约测试规范

每个扩展至少覆盖：

| 契约面 | 必测内容 |
| --- | --- |
| Schema | 当前版本合法/非法样例、旧 minor 兼容、未知 major 拒绝 |
| SOP 编译 | 节点唯一、输入可达、Gate 完整、能力绑定和确定性摘要 |
| 执行结果 | tenant、attempt、lease、大小、摘要、引用和输出 Schema |
| Repository | Memory/PostgreSQL 行为等价、RLS、并发和幂等 |
| Projection | 同一权威事实生成稳定 Studio/CreativeAssetCatalog/Operations 读模型；重建无副作用 |
| API | OpenAPI、服务端 DTO、前端类型、错误码和 action contract 一致 |
| Upgrade | 旧任务继续固定旧版本，新任务采用新版本，回退保持历史可读 |

契约测试失败必须阻断业务包发布；不能通过在消费者中增加宽松解析来掩盖生产者错误。

## 9. 错误与诊断体验

所有开发工具、API 和测试失败使用同一错误结构：

```text
code                 稳定、可搜索、可测试的错误码
message              当前发生了什么
location             文件、JSON Pointer、节点或字段位置
expected / actual    期望与实际摘要
suggestion           一个可执行的下一步
docs_ref             对应规范或运行手册
correlation          request/job/node/attempt/support 引用
```

错误信息不得只返回 `invalid configuration`、原始 SQL、Provider SDK 堆栈或模型全文。批量验证应一次报告互不依赖的全部错误，避免开发者逐个修复后重新发现下一项。

本地诊断包可以包含固定契约、事件摘要、状态转移、执行绑定、脱敏工具调用和投影游标，但不得包含密钥、完整 ContextView、隐藏推理、客户受限正文或本地绝对路径。

## 10. 调试与重放

- 每次本地运行都生成稳定的 `run_id` 和可导出的脱敏诊断摘要。
- 开发者可以从任一 Fixture 重建 Job、Node、Attempt、Gate 和投影。
- 重放默认只重建状态和读模型，不调用执行者、Provider 或其他外部副作用。
- 需要重新执行节点时必须创建新的 Attempt；需要改变固定输入或计划时创建新的 JobRun 分支。
- 时间、ID、执行者选择和 Provider 响应在测试中可注入，业务代码不得直接依赖系统全局状态。
- Studio 问题首先检查 action contract 和投影；Runtime 问题首先检查事件序列、租约和固定版本，禁止让前端猜测底层修复。

## 11. 版本升级与废弃

业务包和平台升级必须提供：

- 兼容 Runtime 范围和依赖契约版本。
- 变更分类：无行为变化、兼容扩展、迁移要求或破坏性变化。
- 旧任务、进行中任务和新任务分别采用哪个版本。
- Fixture、摘要和投影变化说明。
- Preview、Canary、回退和最晚兼容退场阶段。
- 对运营人员可理解的发布说明，不直接暴露内部字段差异。

工具链不得静默升级业务包、Schema major、执行绑定或固定模板。废弃警告必须包含所有者、替代方案、使用量和删除日期；长期无人负责的兼容层视为发布阻断项。

## 12. Time To Hello Workflow

平台使用 `TTHW` 衡量从可工作的仓库到第一个可预览流水线结果所需时间：

```text
起点：开发环境检查通过
终点：最小合法 Fixture 完成确定性执行，且 Studio 预览展示一个可确认结果
```

目标门槛：

- 熟悉仓库的开发者新增一个基于现有原语的最小业务包：`30 分钟内`。
- 首次参与项目的有经验开发者完成同一路径：`60 分钟内`，不依赖口头指导。
- 修改一处无效 Schema 或 SOP 引用后获得可定位反馈：`10 秒内`。
- Level 1 确定性核心测试：`2 分钟内`；更慢测试进入显式集成测试层。

这些是开发效率门禁，不是宣传指标。连续两个迭代不达标时，优先修复模板、错误信息和测试启动成本，不继续增加新的扩展原语。

## 13. Pull Request 与完成检查表

1. 变更属于哪个业务包或平台模块，事实所有者是谁？
2. 是否只使用公开契约，是否修改了 Runtime 内容类型分支？
3. Schema、示例、生成类型、OpenAPI 和 Fixture 是否同步？
4. 最小、成功、无效、边界和升级 Fixture 是否覆盖？
5. 默认测试是否完全确定性且无真实外部调用？
6. 错误是否可定位并给出下一步，日志是否完成脱敏？
7. 旧任务、进行中任务、新任务和回退行为是否明确？
8. Studio 和 Operations 是否读取同一事实的不同投影？
9. Preview、Canary、指标、所有者和运行手册是否齐备？
10. 文档是否明确区分目标能力与当前实现？
11. 保存、批准或交付结果是否按显式规则进入资产目录，并固定底层对象版本与摘要？

## 14. 禁止模式

- 复制另一条流水线后修改 ID 和 Prompt。
- 为单一内容类型增加 Runtime 状态或专用调度表。
- 只在真实模型或真实服务商上才能运行测试。
- 使用生产数据作为 Fixture，或将聊天记录作为调试事实。
- 通过 `map[string]any`、自由文本 Prompt 或前端条件分支绕过契约。
- 在本地成功后直接全量发布，不经过 Preview tenant 和 Canary。
- 为了让测试通过而吞掉未知字段、未知 major、租约冲突或外部结果不明。

## 15. 责任边界

| 事项 | 负责方 |
| --- | --- |
| 业务 Schema、Fixture、校验和内容质量 | CreativePack 所有者 |
| SOP、Gate、能力批准和体验模板 | Catalog / 内容运营产品所有者 |
| Runtime 契约、状态机、调度和重放 | Runtime 所有者 |
| Agent、Connector、Provider 行为与沙箱 | Integration 所有者 |
| Studio/Operations 投影和 action contract | 对应 Experience 所有者 |
| CreativeAssetCatalog 投影、复用契约和重建 | Experience Projection 所有者；事实状态仍由对应业务域负责 |
| 脚手架、统一入口、测试速度和诊断体验 | Platform Engineering |
| 兼容矩阵、Canary、回退和退场 | 变更所有者与平台运营共同负责 |

开发工具本身也受本平台基线约束：保持简单、按真实痛点演进，不为尚未出现的扩展场景提前建立插件市场或通用 DSL。
