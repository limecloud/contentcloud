# 受治理的内容工作流

Content Work OS 把创作和治理分在两个平面：本地工作区保存创作候选和跨会话状态，云端保存项目、不可变提交、人工决定、批准快照与审计。

## 核心对象

| 对象 | 所在位置 | 含义 |
| --- | --- | --- |
| 本地候选（`Local candidate`） | 本地工作区 | 尚未提交的候选内容，可以继续修订 |
| 本地执行记录（`LocalRun`） | 本地工作区 | 一次受约束工作的状态、输入、检查和输出 |
| 任务交接（`Handoff`） | 本地工作区 | 跨会话或跨人员恢复工作的确定性入口 |
| 提交内容版本（`SubmissionRevision`） | 云端 | 用户显式提交的不可变版本 |
| 审核决定（`Decision`） | 云端 | 审核人的批准或退回决定 |
| 已批准快照（`ApprovedSnapshot`） | 云端 | 绑定精确内容版本摘要的正式批准事实 |
| 交付包（`DeliveryPackage`） | 本地与云端投影 | 基于批准快照生成并校验的交付物 |

## 标准流程

```text
读取本地工作区状态
  -> 选择或创建本地执行记录
  -> 固定输入并取得单写者声明
  -> 生成候选并执行确定性检查
  -> 提交前检查
  -> 用户确认精确计划
  -> 创建不可变提交内容版本
  -> Web 工作台人工审核
  -> 形成已批准快照或要求修改
  -> 拉取明确版本
  -> 继续修订或生成交付包
```

## 四条不能混淆的边界

1. **本地保存不等于云端提交。** 只有显式提交（`publish`）才创建提交内容版本。
2. **提交不等于批准。** 只有服务端人工审核决定才能产生已批准快照。
3. **批准不等于交付。** 交付包必须从精确批准快照生成并通过类型化检查。
4. **交付不等于外部发布。** 外部平台的草稿、预览、提交和发布成功是不同状态。

## 为什么每次新对话都读取本地工作区

聊天记录不是项目事实源。`workspace_context` 会读取持久化状态、当前内容版本、活跃执行记录、任务交接状态和修复要求。安装插件、修改环境或转交工作后，应在同一本地工作区根目录中新建对话并重新读取上下文。

## 服务端边界

Content Work OS 服务端保持零执行（`zero-exec`）：不替用户运行智能体、技能、渲染器或客户上传的代码，也不扫描本地工作区。服务端只能看到用户明确提交的范围。
