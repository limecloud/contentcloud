# 运营控制面信息架构

状态：`目标产品设计；第 2 节记录当前真实路由`。

更新时间：2026-08-08。

本文件回答“运营人员进入后台后如何完成工作”，不定义客户创作台的页面，也不把任务运行底层的复杂信息直接暴露给客户。英文路径和对象名是给工程实现用的，页面标题和操作提示优先使用中文。

### 给运营人员的快速理解

| 看到的页面 | 只需要先理解什么 |
| --- | --- |
| 创作产品 | 客户要做什么、分几步、每一步得到什么 |
| 能力与执行 | 平台有哪些可靠的做法，当前哪些能用 |
| 运行诊断 | 哪些客户任务卡住了，下一步怎样安全处理 |
| 平台管理 | 哪些客户开启了什么产品，用量和审计是否正常 |

## 1. 设计原则

### 1.1 按运营任务分区

运营后台的一级导航按“发布产品、治理能力、诊断运行、治理结果、管理平台”分区。“技能包”“执行方式”“外部服务”等技术对象只在“能力与执行”下出现，不能和客户任务混在一起。

### 1.2 一个页面一个主要决定

详情页必须有一个主动作，例如“提交 Canary”“发布版本”“批准绑定”“创建对账任务”。其他动作作为次要动作，并由服务端返回 `allowed_actions`。页面不依赖隐藏按钮或前端猜测权限。

### 1.3 先摘要，再证据，再命令

每个工作面统一采用三层密度：

```text
摘要：当前是否健康、谁受影响、最重要的下一步
证据：版本、摘要、关联对象、时间、延迟、错误和审计
命令：在当前权限和状态下允许执行的有限操作
```

### 1.4 详情页优先于大而全的面板

列表只负责筛选和定位，单页详情负责比较和处理。不要在一个页面同时编辑 Experience、Skill、租户策略和 Runtime 事件；跨对象操作使用明确的关联链接和返回路径。

## 2. 当前页面目录（工程路由附录）

下面的路径主要给产品和工程对照使用。运营人员在页面上看到的是上一节的中文菜单，不需要记住 URL。

```text
/admin
├── /dashboard
├── /products
│   ├── /:product_id
│   └── /:product_id/versions/:version
├── /releases
│   └── /:product_id/versions/:version
├── /customers
│   └── /:environment_id
├── /capabilities
│   └── /:capability_id/versions/:version
├── /executors
│   └── /:executor_id
├── /skills
│   └── /:skill_id/versions/:version
├── /jobs
├── /alerts
├── /tenants
├── /audit
└── /costs
```

数据连接、生成服务、选择规则、外部结果核对、创作结果治理、用户与角色、支持案例等目标工作面没有权威 BFF 时不注册路由。已删除 URL 不保留兼容组件，统一由 `/admin/*` 通配路由返回运营总览。

当前前端边界：

```text
web/src/admin/
├── AdminRoute.tsx            管理员会话与权限边界
├── AdminShell.tsx            当前真实导航和数据刷新
├── context.tsx               关键快照与可选目录隔离
├── routes.ts                 唯一后台路径定义
├── WorkOSConfigPanels.tsx    产品版本和客户开通写工作流
└── views/
    ├── AdminOperationsPages.tsx
    └── AdminRuntimePage.tsx
```

`web/src/admin` 只保留当前运营工作面，不再提供 `AdminWorkOSPage`、占位治理页或旧环境、SOP、Gate、Usage、Runtime 兼容路由。客户 `web/src/studio` 不导入上述 feature。

## 3. 统一工作面结构

所有列表和详情页遵循以下固定布局，减少学习成本：

```text
页面标题 + 当前作用域 + 数据新鲜度
摘要条：风险 / 待处理 / 最近变化
筛选与搜索：默认筛选、保存视图、清除条件
主内容：表格或详情分栏
右侧或底部：审计、关联对象、支持编号
命令区：服务端返回的主要动作和次要动作
```

### 3.1 列表页

- 默认按风险和最近变化排序，而不是按内部 ID。
- 表格列控制在 6-9 个，剩余字段进入详情页。
- 每一行显示状态、版本、更新时间、负责人和 `support_reference`。
- 允许复制稳定 ID，但不把 digest、租户 ID 和内部状态码作为标题。
- 批量动作必须先显示影响数量、版本冲突数和不可执行原因。

### 3.2 详情页

- 首屏显示业务名称、生命周期状态、当前版本和唯一主要动作。
- 版本差异使用字段级 diff；敏感值显示摘要，不显示凭据。
- 关联对象采用链接：Experience -> Capability -> Skill -> Executor -> JobRun -> Effect。
- 历史时间线只读；修复操作产生新版本、Attempt、对账任务或人工决定，不覆盖历史。

### 3.3 数据新鲜度

服务端每个读模型返回：`generated_at`、`projection_cursor`、`staleness_seconds` 和 `freshness_status`。页面必须把“投影延迟”与“对象业务状态”分开显示；陈旧读模型不得显示为实时成功。

## 4. 总览 Overview

总览不是 KPI 大屏，而是当班运营人员的工作队列。默认内容：

| 区块 | 内容 | 主要动作 |
| --- | --- | --- |
| 发布健康 | Draft、Canary、待发布、最近回退的 Experience | 打开发布中心 |
| 能力健康 | 无可用实现、契约失败、过期 Skill、Executor 离线 | 打开能力详情 |
| 运行队列 | 排队超时、租约过期、失败率、Effect unknown | 打开 Runtime Explorer |
| 资产风险 | 权利待办、来源失效、重复候选、投影延迟 | 打开资产治理 |
| 租户变化 | 新启用、暂停、预算接近阈值、策略冲突 | 打开租户策略 |
| 我的待办 | 按角色过滤的审批、对账、支持案例 | 直接处理队列 |

总览顶部只保留 4-6 个可解释指标：活跃任务、阻断任务、待处理高风险项、发布健康、投影延迟和当日成本。每个指标必须能钻取到筛选后的列表，禁止点击 KPI 后丢失上下文。

## 5. 创作产品：Experience Release Center

这是运营后台的核心工作面。运营人员维护“客户能使用的产品版本”，而不是单独编辑一组 SOP 表。

### 5.1 Experience 详情结构

```text
Experience Release
├── 目标与客户步骤
├── 输入与资料要求
├── SOP / Stage / Gate
├── Required Capabilities
├── 结果呈现与资产策略
├── 执行绑定预览
├── 租户启用范围
├── 验证、Canary 与回退
└── 版本、差异与审计
```

页面编辑的是受限原语：步骤标题、输入 Schema、Gate 类型、结果展示、能力引用和租户资格。不能在页面粘贴任意脚本、任意 Prompt 或无限流程图。

### 5.2 发布工作流视图

发布中心显示一条明确的生命周期：

```text
draft -> linted -> preview -> canary -> published -> deprecated -> retired
                         |          |
                         +-> failed +-> rolled_back
```

每个状态显示进入时间、操作者、校验结果和下一步条件。发布按钮只有在服务端返回全部门禁通过时可用。

### 5.3 执行绑定预览

发布前显示每个 Required Capability 的候选：

| Capability | 选中实现 | Executor | 版本摘要 | 数据等级 | 副作用 | 成本上限 | 风险 |
| --- | --- | --- | --- | --- | --- | --- | --- |

预览必须说明“为什么选中”“哪些租户会不同”“无可用候选时如何阻断”。正式运行使用固定 `ExecutionBindingSnapshot`，页面上的预览不能代替运行快照。

## 6. 能力与执行

### 6.1 Capability 能力目录

Capability 页面回答“平台承诺提供什么”，字段包括：用途、输入/输出 Schema、数据分类限制、副作用等级、成本/超时、已批准实现和近 7 天健康摘要。

允许动作：创建草稿、提交验证、停用新引用、查看影响范围。禁止直接把某个 Skill 改名为 Capability 或在能力页面编辑执行脚本。

### 6.2 Executor 执行者

Executor 页面回答“谁在什么信任边界内执行”。类型可为 `deterministic_worker`、`codex_client`、`claude_code_client`、`provider_adapter`、`human_runbook` 等。页面显示区域、心跳、并发、数据访问级别、当前租约和失败趋势。

Executor 健康异常只能影响候选资格或触发预先声明的回退，不允许运营人员在运行中手工把任务改绑到另一个执行者。

### 6.3 Skill 技能包

Skill 是 Capability 的版本化实现。详情页必须同时显示：

- `skill_id`、版本、digest、发布状态和拥有者。
- 所实现的 Capability、兼容 Runtime、输入/输出 Schema。
- 工具白名单、网络策略、数据分类上限和副作用类型。
- Fixture、契约测试、Canary 证据、成本模型和支持手册。
- 被哪些 Binding Policy、Experience Release 和租户使用。

Skill 与 Experience 分开发布。Skill 可以先进入批准目录，只有绑定策略引用它后才会影响新任务。

### 6.4 Connector / Provider

Connector 表示数据入口或外部系统连接，Provider 表示媒体、模型或平台服务适配。两者都不等同于 Skill：

```text
Capability -> Skill implementation -> Executor
Skill/Executor -> Connector or Provider dependency
```

凭据只显示引用和健康状态，不显示明文。连接测试必须使用受限测试请求，并记录 Effect 类型和费用。

## 7. Binding Policy 绑定策略

绑定策略是独立产品面，不嵌入 Experience 或 Skill 页面。页面分为：

1. 条件：租户、项目、区域、数据分类、合规标签、预算和时间窗。
2. 候选：批准的 Skill/Executor/Provider 组合及优先级。
3. 限制：并发、超时、成本、工具、网络和副作用上限。
4. 回退：仅能选择不会扩大披露、权限、副作用或预算的候选。
5. 模拟器：用指定租户、输入分类和运行时版本计算命中规则。

模拟器输出：命中规则、被排除候选及原因、最终绑定、是否可回退、预估成本和需要的审批。保存策略前必须提供受影响的 Experience、租户和活跃任务数量。

## 8. Runtime Explorer

Runtime Explorer 是诊断产品，不是数据库管理器。详情页按以下顺序呈现：

```text
业务关联：租户 / 项目 / WorkTask / Experience Release
执行计划：JobPlanRevision / ExecutionBindingSnapshot 摘要
节点：状态、依赖、输入输出引用
尝试：Executor、租约、心跳、错误、用量
外部操作：Effect 请求、结果、对账和补偿
人工门禁：等待者、固定版本、决定
事件审计：时间、游标、关联 ID
```

允许运营动作由当前状态决定，例如暂停调度、取消未开始节点、创建新 Attempt、启动 Effect 对账、请求人工决定和打开支持案例。禁止“强制成功”“删除事件”“重复提交未知副作用”。

## 9. 资产治理

资产治理管理客户可见创作结果的运营风险，不替代客户资产页面。四个工作面：

- 创作结果目录：类型、来源、状态、租户范围、使用次数和投影延迟。
- 权利与来源失效：失效记录、影响的结果和阻断的新引用。
- 重复与合并候选：相似结果、证据、建议动作和人工确认。
- 投影重建：游标、失败分片、重建预览和无副作用重放。

治理命令只能作用于投影、关系和待办。Source、RightsRecord、Approval、Artifact、Delivery 等权威事实必须通过拥有域命令变更。

## 10. 平台治理

### 10.1 租户与策略

租户页以“已启用 Experience、数据策略、预算、区域和支持状态”为中心。平台运营可启用已发布版本、设置有限覆盖项和暂停新任务；不能替租户修改其业务内容或批准结果。

### 10.2 审计

审计页支持按操作者、租户、对象、命令、风险等级和时间筛选。每条记录必须可追溯到请求、版本、前后摘要和结果，不显示凭据、完整提示词或受限资料。

### 10.3 用量与成本

成本页按租户、Experience、Capability、Executor、Provider 和时间窗聚合。数字必须标明结算状态和数据延迟，不能把估算费用显示为已结算事实。

## 11. 权限体验

权限不通过隐藏导航表达。服务端返回：

```json
{
  "allowed_actions": [
    {"id": "submit_canary", "enabled": true, "reason": null},
    {"id": "publish", "enabled": false, "reason": "需要双人批准"}
  ],
  "scope": {"tenant_ids": ["t_demo"], "environment": "staging"}
}
```

禁用动作仍可见，但必须给出业务可理解的原因和完成条件。高风险动作使用确认页，展示影响对象、版本差异、预计费用、回退方式和审计说明。

## 12. 响应式、可访问性与验证

- 遵循根目录 `DESIGN.md`：深松绿侧栏、冷白工作面、中性边框、多组对象色；不把运营后台做成单一绿色大屏。
- 桌面基准 `1440 x 1000`，移动基准 `390 x 844`，最低 `320px`；表格在窄屏转为可横向滚动的稳定列或详情列表。
- 触控目标不小于 `44 x 44px`；图标按钮使用 Lucide 并提供名称；状态不只靠颜色表达。
- 加载、空、错误、无权限、陈旧、部分完成和成功状态必须有专门设计。
- 验证指标：运营完成一次发布的步骤数不超过 7 个；从告警到关联 JobRun 不超过 3 次跳转；从 Skill 反查受影响租户不超过 2 次跳转；误操作率和回退成功率纳入试点验收。
